# React 中什么情况下不应该用 `memo`

`React.memo` 不是默认优化项。

它的作用不是“阻止重渲染”，而是在条件满足时让 React 走一次 `bailout`，跳过这个函数组件的执行和它下面那段子树的协调工作。这个判断依赖浅比较、引用稳定性，以及这条路径上没有别的更新源把它重新拉进来。

所以，`memo` 只适合一种情况：**组件多数时候没有变，但父组件反复重渲染把它连带执行了很多次**。

一旦不满足这个前提，它就很容易变成负优化。

## 一、底层上，`memo` 到底省了什么

`React.memo` 省掉的是：

- 函数组件本身的执行
- JSX 生成
- 这次子树的协调工作

它也会带来成本：

- props 比较
- 额外的边界判断
- 对引用稳定性的依赖
- 为了配合它而引入的 `useMemo`、`useCallback`

结论很直接：`memo` 不是免费收益，它是在用比较成本换渲染成本。

只有当被省掉的工作确实更贵，它才值得保留。

## 二、最不该用的几类场景

### 1. 组件很轻

如果组件只是少量文本、简单布局、几个普通节点，渲染成本本来就低。

这时再加 `memo`，收益通常不如一次浅比较。

轻组件默认不该包 `memo`。

### 2. props 每次都在变成新引用

这是最常见的失效原因。

```tsx
<MyComp onClick={() => doSomething(id)} />
<MyComp style={{ padding: 8 }} />
<MyComp items={[1, 2, 3]} />
```

内容看起来没变，引用实际上每次都变。`memo` 默认是浅比较，所以会一直失效。

如果为了让它生效，开始到处加 `useMemo` 和 `useCallback`，通常说明你在围绕优化写代码，而不是围绕业务写代码。

### 3. 组件本身就有别的更新源

如果组件主要靠这些东西更新，`memo` 的意义就很小：

- `useState`
- `useReducer`
- `useContext`
- 外部 store 订阅
- React Query、Redux、Zustand 之类的数据源

尤其是 `useContext`。只要 context value 变了，消费它的组件还是会更新。

这类组件不是 `memo` 的好目标，因为它们的变化不是“无意义重复渲染”，而是业务上真实存在的更新。

### 4. 你还没确认它是热点

这是最重要的工程原则。

不要因为“看起来会重渲染”就上 `memo`。先确认它是不是实际瓶颈。

很多真正耗时的地方不在子组件，而在：

- 父组件里的数据处理
- 列表映射
- 某个昂贵 hook
- 上下文广播过大
- 虚拟列表没做

如果热点不在这里，`memo` 基本不会改变整体性能。

### 5. 为了让 `memo` 生效，代码明显变复杂

这个判断很简单：

- 加了 `memo`
- 然后又被迫稳定一堆函数引用
- 稳定一堆对象引用
- 手动维护一串依赖关系

这通常不是优化成功，而是优化成本已经超过了收益。

一旦代码复杂度开始围着缓存打转，后续改动就会变脆。

### 6. 问题本质是架构切分，不是局部渲染

如果状态放得太高、props 传得太深、context 粒度太粗、一次更新波及太多子树，`memo` 只是补丁。

这时更应该先改：

- 状态下放
- context 拆分
- props 收窄
- 组件边界重切
- 列表虚拟化

结构不对，`memo` 只能延缓症状。

## 三、什么时候它才值得用

可以把 `memo` 的适用条件压缩成三句：

- 组件渲染贵
- 父组件经常重渲染
- 这个组件的 props 大多稳定

典型场景通常是：

- 复杂图表
- 大表格里的重型 item
- 结构稳定但渲染代价高的区域

这类场景里，`memo` 才有机会把“重复计算”变成“可跳过工作”。

## 四、工程上怎么判断

我一般只问三个问题：

1. 它是不是实际热点？
2. 它的 props 稳不稳定？
3. 它的渲染代价够不够高？

三个问题里有一个答案是否定的，就先别加 `memo`。

顺序也很重要：

1. 先用 React DevTools Profiler 看真实耗时
2. 再确认是不是父组件连带导致的重渲染
3. 再看 props 能不能稳定
4. 最后才考虑 `memo`

`memo` 是最后一层局部优化，不是第一反应。

## 五、不要把 `memo`、`useMemo`、`useCallback` 绑成默认模板

这三个东西相关，但职责不同：

- `memo` 跳过组件执行
- `useMemo` 缓存计算结果
- `useCallback` 稳定函数引用

它们不是一套必须一起上的“性能套餐”。

如果组件本身不重、props 也不稳，那为了配合 `memo` 去制造缓存，往往是在用更高的复杂度换一个不确定的收益。

如果项目已经启用了 React Compiler，这个判断还要更谨慎。很多手写的 `memo` 需求会被编译器覆盖，没必要先入为主。

## 结论

不该用 `memo` 的情况，本质上就三类：

- 渲染本来就不贵
- 输入本来就不稳定
- 更新本来就有正当来源

更具体一点：

- 轻组件别默认 `memo`
- props 每次新引用时别硬套 `memo`
- 自己就靠 state / context 更新的组件别指望 `memo`
- 没测出热点前别优化
- 为了生效而明显增加复杂度时别用
- 架构问题别拿 `memo` 补

`memo` 适合切断无意义的重复计算，不适合对抗真实变化。

如果一段代码需要很多缓存才能“看起来优化成功”，通常说明你优化错了层。
