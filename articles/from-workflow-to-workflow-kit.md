# 从 Workflow 到 Workflow Kit：一套 AI 任务机制如何演化成基础设施

最初，我们只想解决一个简单问题：AI Agent 执行复杂任务时，怎样在中断以后继续工作？

第一版方案很直接——为每个任务创建一个 Markdown 目录，记录目标、计划、研究过程、任务清单和最终结果。

它确实解决了聊天上下文容易丢失的问题。但随着任务增多、多个 Agent 并行、工具开始跨项目复制，这套方案逐渐暴露出更深的问题。

最终，我们发现需要设计的已经不是一组 Workflow 模板，而是一套可安装、可升级、可校验的 Workflow Kit。

这篇文章讨论的就是这段演化过程。

## 第一阶段：用 Markdown 保存执行上下文

复杂任务通常不会一次完成。它可能经历需求澄清、原因调查、方案选择、分步实现和最终验收，中间还可能被打断或交给另一个 Agent。

如果所有信息都留在聊天中，恢复成本很高：新的执行者需要重新判断目标、事实、假设和当前进度。

于是，最初的 Workflow 使用一组 Markdown 文件保存任务状态：

```text
workflow/
├── brief.md
├── plan.md
├── research.md
├── tasks.md
└── result.md
```

这套机制解决了两个核心问题：

- 任务状态不再完全依赖聊天上下文
- 研究、计划和结果有了稳定的恢复入口

同时，根据任务的不确定性，Workflow 被分成三种模式：

- `quick`：目标明确、范围有限
- `discovery`：问题原因或正确方案未知
- `implementation`：目标明确，但需要设计、执行和验收

到这里，Workflow 仍然只是一个文档协议。它告诉 Agent 应该记录什么，却无法保证这些记录始终正确。

## 第二阶段：文档协议无法维护结构一致性

当 Workflow 数量增加后，单纯依赖 Markdown 和 Agent 自觉维护，开始出现一系列问题：

- 新任务可能使用重复 ID
- Workflow 归档后，旧 ID 可能被再次使用
- 一个外部任务可能同时绑定到多个 Workflow
- 父子任务可能引用不一致，甚至形成环
- 任务内容已经完成，但仍存在活跃子任务或执行绑定
- 机器状态已经变化，汇总页面却没有同步

这些问题有一个共同点：它们都不是语义问题，而是结构问题。

“当前证据是否足够”需要 Agent 判断；“一个 ID 是否重复”不需要。后者如果仍依靠提示词约束，相当于让概率模型执行本应确定的规则。

因此，第二阶段引入了确定性 CLI，由程序负责：

- 创建 Workflow 和分配稳定 ID
- 修改状态和阶段
- 建立父子关系并阻止环
- 维护外部任务绑定
- 生成汇总视图
- 校验全项目一致性
- 在满足约束时归档

这一步是整个设计的分界线。

Workflow 不再只是“建议怎样写”，而是开始定义“哪些状态绝不能出现”。模板负责内容，CLI 负责不变量。

## 第三阶段：把系统拆成三个责任层

CLI 解决了结构一致性，却没有解决另一个问题：哪些任务应该创建 Workflow？Agent 应该怎样记录事实与假设？不同项目的安全边界又由谁决定？

如果把这些内容全部写进 CLI，工具会和具体项目强耦合；如果全部写进提示词，又会失去确定性。

因此，系统最终拆成三个独立层次。

### Workflow Core

Core 是确定性工具，只负责结构操作和数据完整性。

它不知道业务含义，也不判断方案是否正确。它只保证 ID、状态、关系、绑定和归档满足规则。

### Agent Skill

Skill 定义 Agent 的行为方式：

- 什么任务值得创建 Workflow
- 如何选择 quick、discovery 或 implementation
- 如何区分事实、假设和决策
- 如何维护明确的 Next Action
- 完成前需要留下哪些验收证据

### Project Policy

项目策略保存具体项目的权限和业务边界，例如：

- 哪些操作需要用户确认
- 是否允许操作远程环境
- 是否允许自动提交和推送
- 稳定知识最终进入哪里

这三个层次分别回答三个问题：

```text
Core：状态怎样合法变化？
Skill：Agent 应该怎样工作？
Policy：这个项目允许做什么？
```

分层以后，通用能力与项目规则不再混在一起，Workflow 才具备跨项目复用的基础。

## 第四阶段：从“复制文件”到可升级的工具包

当这套机制需要安装到更多项目时，新的问题出现了。

最简单的分发方式是复制 CLI、模板和 Skill。但复制以后，各项目会独立修改这些文件，逐渐产生版本漂移：

- 不知道项目使用的是哪个版本
- 不知道哪些文件被本地修改过
- 更新可能覆盖项目自己的规则
- 工具文件可能与任务数据混在一起
- 新版模板与旧版数据结构可能不兼容

因此，Workflow 需要从项目内部约定演化成一个有版本边界的 Workflow Kit。

最终采用项目内 vendoring：把运行所需的 CLI、Skill 和模板复制进项目，使项目可以离线、自包含地运行；同时用 manifest 记录工具版本和受管文件的 SHA-256。

安装与升级遵循几个严格规则：

- 工具受管文件与项目任务数据分离
- 首次安装遇到不同内容时拒绝覆盖
- 更新发现本地修改时拒绝覆盖
- 只有显式强制更新才允许替换
- 替换前必须自动备份
- 项目配置只在缺失时创建，永不覆盖
- Workflow 数据永远不属于安装器的受管范围

这套机制解决的并不只是“怎样复制文件”，而是一个更根本的问题：

> 哪些内容属于工具上游，哪些内容属于使用工具的项目？

安装器真正管理的是所有权边界。

## 第五阶段：让 Workflow 可以被验证

一个系统能够创建任务，不代表它值得信任。它还必须能够证明自身没有进入错误状态。

因此，Workflow Kit 增加了全项目校验，检查：

- 目录名、ID 和 slug 是否一致
- active 与 archive 中是否存在重复 ID
- 状态与所在目录是否匹配
- 外部任务是否被重复绑定
- 父子关系是否双向一致
- 是否存在关系环或丢失对象
- 生成视图是否与机器状态一致
- 模板占位符是否仍未处理

同时，所有结构写入使用项目级锁和原子替换，避免多个进程同时修改，或中断后留下半个 JSON 文件。

到这一步，Workflow 才真正具备了基础设施的基本属性：不仅能够工作，还能够发现自己何时不可信。

## Workflow Kit 最终解决了什么

从最初的 Markdown Workflow 到完整的 Kit，解决的问题可以分成四层。

### 1. 上下文恢复

任务目标、关键事实、当前进度和下一步不再只存在于聊天中。Agent 被中断或替换后，可以从项目文件恢复。

### 2. 结构可靠性

稳定 ID、状态机、父子关系、任务绑定和归档条件由确定性工具维护，不再依赖 Agent 每次都正确理解规则。

### 3. 多 Agent 协作

任务所有权、父子关系和外部绑定有明确事实源，减少重复执行、关系冲突和状态覆盖。

### 4. 跨项目复用

CLI、Skill 和模板可以安全安装和升级，同时保留每个项目自己的配置、任务数据和策略。

## 这段演化带来的核心认识

Workflow Kit 并不是一开始设计出来的。

它是在实际使用中，沿着一条清晰的因果链逐步形成的：

```text
聊天无法可靠恢复任务
→ 用 Markdown 保存执行上下文
→ 文档无法保证结构一致性
→ 引入确定性 CLI
→ 通用规则与项目规则相互耦合
→ 拆分 Core、Skill 和 Policy
→ 手工复制导致版本漂移
→ 引入 manifest、安装器和升级保护
→ 多任务与多 Agent 带来并发风险
→ 增加锁、原子写入和全局校验
```

这条路径说明：当 AI 开始承担长期、复杂、可能中断的任务时，问题很快就不再是“怎样写一份更好的提示词”，而是“怎样围绕概率模型建立确定性的执行基础设施”。

Workflow 是起点。Workflow Kit 则把执行记忆、结构约束、项目策略和版本治理组合成了一套可以长期使用的系统。
